Step 1 / InstallFive minutes
opencode

Install the CLI, then point it at your skills.

Install

curl -fsSL https://opencode.ai/install | bash

# or, if you prefer npm
npm install --global opencode-ai

opencode --version
1.18.14

A terminal-native coding agent. It reads your repo, edits files, runs commands, and asks before anything destructive.

A four-line launcher, once

# ~/.local/bin/opencode
#!/usr/bin/env bash
export OPENCODE_DISABLE_CLAUDE_CODE_SKILLS=1
export OPENCODE_DISABLE_EXTERNAL_SKILLS=1
exec ~/.opencode/bin/opencode "$@"

These two flags make OpenCode load exactly the skills you list and nothing else. Without them it also auto-discovers ~/.claude/skills and ~/.agents/skills, and you get duplicate names and unpredictable behaviour.

Setup: 5 minutes ✓ A coding agent in every repo you work in ✓ Predictable, explicit skill loading
Source: ~/.local/bin/opencode, personal-skills/README.md02 / 10
Demo live if possible: run opencode in a real repo and ask it something small. The launcher is the only non-obvious part and it exists for one reason — a name-based allowlist cannot tell two same-named skills apart when they come from different directories, so we disable discovery entirely and list paths explicitly. Mention that the permission block in opencode.jsonc is worth copying too: everything allowed by default, with ask on sudo, rm, git push, gh pr create, docker push and cloud CLIs.

Why this is the easy step

  • No API key to request, paste, or store.
  • No new subscription, no procurement, no cost centre.
  • Same entitlement as Copilot in your editor — this is just a better front end for it.
  • Tokens refresh automatically, so it keeps working.
Worth knowing

The agent inherits your shell environment, so it can see whatever your gh token can do. Keep that PAT scoped to what you actually need — good hygiene regardless of agents.

This is the step people expect to be hard and it is not. Stress that there is no key handling at all — it is a device OAuth flow like signing into any other GitHub app. If someone asks about cost: this consumes the Copilot entitlement we already pay for. The PAT note is a hygiene tip, not a warning about OpenCode specifically; the same is true of any tool that runs commands on your behalf.
Step 3 / InstructionsThe cheapest big win
instructions/opencode-development.md — 24 lines

Stop the agent over-engineering your two-line fix.

Out of the box, agents love ceremony: a plan, a design doc, a test-first ritual and a summary, for a one-line change. One short file, loaded into every session, fixes it.

inspect
>
edit
>
verify
>
report

Plus: smallest correct change, preserve unrelated edits, resolve small ambiguities from the repo instead of asking, verify with the narrowest command that proves the claim.

The line that does the heavy lifting

"File count, feature work, and behavior changes alone are not formal-workflow triggers. If material risk appears during direct execution, stop and escalate then."

Escalate only when risk is real

Architecture or public APIs · security, privacy, authorization · migrations or destructive operations · cross-system ambiguity · weak verification · unfamiliar tech with a high cost of failure.

Wire it up once in opencode.jsonc under instructions, and it applies in every repo you open.

Setup: 5 minutes ✓ Copy the file, change nothing else ✓ The single biggest quality-of-life jump here
Source: instructions/opencode-development.md04 / 10
If people only take one thing away, make it this slide. It costs nothing, needs no team agreement, and it is the difference between an agent that feels like a colleague and one that feels like a process consultant. The counter-intuitive insight worth stating: most of the effort in this whole system went into making the agent do less, not more. Twenty-four lines, loaded every session, no per-repo setup.
Step 4 / Repo knowledgeWrite a lesson once
template-pyramid-app / AGENTS.md

The things that bite everyone, written down once.

  • The silent trap. A model not imported in models/__init__.py is never mapped — the table just does not exist, with no error.
  • Test isolation is per module, not per test. A test that passes alone can fail in suite order.
  • Views need a permission, or they are reachable unauthenticated.
  • Where things live: routes, models, views, migrations — so the agent extends the structure instead of inventing one.
  • Alembic reality: most apps set target_metadata = None, so --autogenerate silently writes an empty migration.
  • Secrets and database rules the agent must never cross.

How selection works

A skill is a markdown file with a name and a description. The description is the trigger. Ask for a review and code-review loads itself; ask for a two-line fix and nothing loads at all.

Why this beats a giant prompt

Instructions stay short, so they are actually followed. Expertise arrives only in the sessions that need it — no token cost and no ceremony the other 90% of the time.

✓ A skill is just a markdown file ✓ Add one in an afternoon ✓ Reviewed like code, in a repo

Step 6 / EvidencePrompt engineering with a test suite
tests/evaluate_skills.py

How do you know the skills actually help?

33

Trigger cases. Did the right skill load — and, just as important, did nothing load when it should not? 13 cases exist purely to prove the agent stays out of the way.

17

Outcome cases. Did the skill change the result? Each runs twice: once normally, once against a baseline with the skill removed. If the baseline already passed, the skill was not needed.

58

Unit tests + validator. Schema checks, dead-link detection, and a rule that every core skill keeps at least 3 trigger and 3 outcome cases. Runs on every push.

# adding a case is this small

The contribution loop

Skill did something silly in your session? Add a case describing what should have happened. It becomes a permanent regression test, and the next person never sees that behaviour. This is the easiest way to contribute.

Sources: tests/evaluate_skills.py, tests/fixtures/, .github/workflows/test-skills.yml07 / 10
This is what turns a folder of prompts into something maintainable. The A/B baseline is the key idea and worth dwelling on: without it you cannot tell a skill that works from a model that would have done the right thing anyway. Cases that pass without the skill are surfaced for review as evidence the skill may be redundant. Close on the contribution loop — a five-line JSON case is a genuinely welcome pull request and needs no knowledge of the harness.
Step 7 / VerificationMake the agent prove it
agent-env

It runs the real gates, and cannot touch your stack.

agent-env doctor  .  # check the host
agent-env prepare .  # build + start, once
agent-env check   .  # the full gates
agent-env exec    . -- pytest tests/test_x.py
agent-env down    .  # tear it all down

# the gates it runs
uv run ruff check .
uv run mypy .          # where CI enables it
uv run pytest
uv run coverage report --fail-under=N

Install once per host:
uv tool install git+https://github.com/lkroon/agentic-dev-tools

  • Dedicated to your checkout. The Compose project name hashes the absolute path, so it can never land on your own running containers — or on another checkout of the same repo.
  • No published ports, no renamed containers. Your docker compose up keeps working while the agent runs a full suite.
  • Your :latest image survives — the build is retagged :agent-env.
  • The agent cannot quietly weaken the gates — they are assembled by the launcher, outside the repository.
  • Honest reporting is enforced: if pytest fails, coverage is reported as unknown, never as passing.
  • Disposable database, deleted on teardown. Nothing shared, nothing staging.
✓ No more "it works on my machine" from your agent ✓ No host pollution ✓ Same gates for everyone
Sources: skills/agent-env/SKILL.md, agentic-dev-tools/08 / 10
The pitch: an agent that says "done" is worthless; an agent that says "ruff clean, 412 tests passed, coverage gate passed, exit 0" is a colleague. The collision-avoidance detail lands well with anyone who has had a stray container eat their port 5432. Be precise on the coverage threshold — the launcher applies a fixed value today and confirming it against the reusable CI workflow is on the gaps slide. Demo agent-env doctor if there is time; it prints every derived value and the file it came from.
09 / GapsWhere the work is
Honest status

What is not finished yet.

The fleet rollout

The contract lives on an unmerged branch; origin/main of the template does not carry it yet, so most apps have no AGENTS.md.

blocks: steps 4 at fleet scale

App-specific docs have nowhere to go

The sync merges with -X theirs, so anything an app adds to AGENTS.md is overwritten on the next sync — silently, with no conflict.

blocks: per-app instructions

Setup is not reproducible

My config is hand-maintained absolute paths. The skill manifest lists 14 entries; my config lists 13. Nothing keeps them in step.

blocks: everyone but me

agent-env is isolation, not security

It stops collisions, not exfiltration: no network egress limits, and the build token persists in the image. Its own audit command measures this and currently fails.

blocks: running untrusted code

The coverage gate is assumed

The launcher hardcodes a threshold rather than reading it from the reusable CI workflow. If the real number differs, results mislead in both directions.

blocks: claiming CI parity

Evals run on request only

The model-backed suites cost tokens, so they are manual. Regressions can land unnoticed. Version drift between my host and CI does not help.

blocks: trusting the skills long-term
The real bottleneck

It is not the number of skills — fourteen is plenty. It is that none of this is reproducible by a second developer yet, which caps the whole thing at one person no matter how good it gets. That is a solvable problem, and it is the most valuable thing anyone here could pick up.

Verified against: origin/main, sync.py, opencode.jsonc, discovery.py, agentic-dev-tools/README.md09 / 10
Say plainly that this slide exists so nobody adopts the setup on a wrong premise and gets burned. None of these are reasons to wait — steps 1 to 3 are unaffected by every gap listed here. Gap two is the one with a design consequence: because the sync always prefers the template, app-specific instructions need their own file rather than a section in AGENTS.md. Gap four matters if anyone plans to point this at untrusted dependencies; it is a collision boundary, not a security boundary.

Where this goes next

The best version of this is not mine.

Every piece is a text file in a repository — reviewable, testable, and improvable by anyone. The fastest way to make agentic development good here is for five people to use it and complain loudly.

Start at step 1 today Steps 1–3 need no team decision
  1. 01Try steps 1–3 this week. Fifteen minutes. Then tell me what annoyed you — that feedback is worth more than another skill.
  2. 02Land the fleet contract and adopt a layered split: the template owns AGENTS.md, each app owns a file the sync never touches.
  3. 03Write the bootstrap script. Generate the config from the manifest so setup is one command. Highest-value first contribution, roughly a day.
  4. 04Add an eval case whenever a skill misbehaves. Five lines of JSON, permanent regression cover, no harness knowledge needed.
  5. 05Decide agent-env's status — team-standard verification or labelled pilot — and confirm the coverage threshold against CI.
  6. 06Bring your repo's hard-won lessons. If something has bitten you twice, it belongs in an AGENTS.md, not in your head.
